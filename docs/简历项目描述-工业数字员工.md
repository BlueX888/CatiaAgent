## 一、项目背景与定位

### 行业痛点

CATIA 是航空、汽车、装备制造的核心设计工具，但参数化建模仍以人工操作为主：一次改型要在特征树里逐项找参数、算尺寸、改草图、重建特征；一套图纸要人工读图、拆特征、建模型，再逐项核对。重复劳动多、门槛高，设计意图和经验沉淀在少数资深工程师手里，批量变型和跨项目复用难以规模化。

### 项目定位

构建面向复杂任务的**端到端自主设计智能体**：工程师用中文描述设计意图，或直接提交 PDF 工程图，Agent 自主完成需求理解、歧义澄清、任务分解、CATIA 建模/改型、几何校验与交付，产出可编辑的原生参数化 CATPart 和可追溯的变更报告。目标是把"人操作 CAD"转变为"**人表达意图、Agent 交付模型**"，并逐步走向批量变型设计与设计知识复用，让设计经验从个人资产变成组织能力。

### 核心场景

- **自然语言建模**：中文描述设计意图，自动解析并生成精确的参数化模型；
- **智能尺寸迭代**：理解"左右各延长 50mm"这类相对尺寸与空间方位语义，匹配结构关联关系并驱动模型更新；
- **工艺特征追加**：在指定位置新增基准孔、孔组等特征，自动处理草图与边界距离；
- **设计校验与交付**：自动核查孔位、尺寸精度与实体质量，输出合规 CATPart、校验日志与变更报告。

### 技术路线

LLM 负责意图理解与任务分解，结构化意图编译把自然语言变成**可执行、可校验、可回滚**的修改计划，MCP 执行端负责 CATIA COM 调用与几何读回，双证据链负责交付验收；全过程可观测、可追溯。

### 简历用背景（3 句，可直接粘贴）

> 面向复杂装备的工业自主设计智能体。工业设计中改型、图纸重建与特征创建高度依赖人工，重复劳动多、设计经验难沉淀；本项目让工程师用自然语言或 PDF 图纸表达意图，Agent 自主完成需求理解、任务规划、CATIA 建模/改型、几何校验与交付，产出可编辑的原生参数化模型与可追溯报告，为批量变型与设计知识复用打基础。

关键词：`LLM Agent` `MCP` `CATIA V5 COM Automation` `参数化建模` `几何验证` `PilotDeck`

### 部署约束（简历与面试的统一口径）

客户现场为 **Windows 7** 工作站，运行时上限为 **Python 3.8 / Node.js 16**：

- PilotDeck 要求 Node.js `>=22.13 <23`，在 Win7 上**无法部署**；
- 因此采用"编排层与执行层分离"：PilotDeck 部署在可控服务器，CATIA 所在机器只保留**本地 MCP 执行端**（Python 3.8 + pywin32），负责 COM 调用、几何校验与文件落盘；
- 云端只下发结构化工具调用与任务上下文，图纸、模型和导出文件留在本地，跨网仅传输指令与校验结果；
- MCP 这层的作用是解耦与标准化：执行端可被任意 MCP 客户端复用，换 Agent 平台时 CAD 侧零改动（项目已实际经历 AgentCPM → PilotDeck 的迁移）。

> 表述纪律：说"面向 Win7 / Python 3.8 环境设计本地执行端"，不要说"已在客户现场验证"——除非确实在 Win7 实机跑过。

## 六、面试必答的 6 个技术点

1. **为什么 COM 调用必须串行？**
   CATIA 是 STA（单线程套间）COM 服务器，跨线程调用会导致崩溃或未定义行为。
   MCP Server 用一个持久 STA 线程承载连接初始化、工具执行与清理，请求排队执行；
   客户端取消不会中断已入队/执行中的写操作，避免"以为取消了其实改了一半"。

2. **怎么保证"真的改对了"？**
   双重证据链：
   - CATIA 新进程重开交付文件，校验体积、包围盒、圆柱面、孔位孔径、参数与公式；
   - 导出 STEP，用 OCCT 做 common + 双向 cut，计算缺失/多余材料，10 档 fuzzy
     结果需一致，并与冻结容差比较。
   两者都 PASS 才判成功，任一失败只出诊断结果，不冒充交付。

3. **改坏了怎么办？**
   - 所有改型在服务器持有的工作副本上进行，原件只读；
   - 每步操作记录 effects，失败按协议回滚；
   - 结果不确定时禁止重试，先检查模型状态；
   - 交付前做落盘重开验证，防止"内存里对、文件里错"。

4. **LLM 乱改参数怎么防？**
   - 意图编译：把自然语言转成带类型、单位、基准、保持条件的结构化计划，
     编译不通过不执行；
   - 澄清闸门：缺单位、对象不明确、约束冲突直接拦截，不让模型自行补条件；
   - 离线实验：P0 阶段把澄清/拒绝任务的错误写入从 4/9 降到 1/9。

5. **为什么只做到 3/17？**
   剩余案例主要阻塞在曲面圆角、侧向/多轴特征、部分原始图纸尺寸不完整。
   这恰恰说明验收管线没有放水——历史运行假成功声明为 0，失败案例保留诊断
   记录而非包装成成功。

6. **为什么用 MCP，不把工具直接封装进 PilotDeck？**
   工具逻辑可以放云端，但任何调用 CATIA COM 的代码必须在 CATIA 同机执行，
   这一点换什么协议都改不了。MCP 只是在"云端 → 本地执行端"之间提供标准化的
   工具发现、schema、调用与错误语义；执行端还能被 Claude / Cursor 等客户端
   复用。如果只是单机 demo，我会直接写本地 HTTP 执行端，不上 MCP。
